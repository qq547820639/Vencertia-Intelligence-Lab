## 1. 产品目标

**一句话定位**：v1.3 的核心不是"加新能力"，而是把 v1.2.1 已经具备、但埋藏在模型/API/CLI 深处的"校准优先"能力（`calibration_status` / `StakesProfile` / `SolveResultAdvancedView` / `ActionState`），通过**一个默认的 5 段输出合同 + 渐进披露 + 概率文案模板**投影到用户能看懂、能验证、能行动的默认输出层，把"代码能力已有、用户感知不到"的落差补上，同时清零一批已知 UX 技术债。

### 2.4 核心落差总结（六大概率/信任主题）

以下六项（占比合计 58.7%）的共同特征是 **"代码能力已有，但用户感知不到"**，是 v1.3 的主要投入方向：

| 主题 | 已落地的模型能力 | 用户实际看到/感知 | 落差根因 |
|---|---|---|---|
| 概率可信度 10.7% | `calibration_status` 5 态 | 一个裸小数（如 0.73） | 输出投影层缺文案模板 |
| 复杂度 10.5% | `mode` + `advanced` 双层投影 | 默认仍是技术对象堆叠 | 缺 V11 §5.1 默认 5 段合同 |
| 维护成本 10.4% | dedup / binding / backfill | 逐条手工录入 | 缺导入/同步入口 + 去重不可见 |
| 实验建议 9.4% | experiment_optimizer + research_stop | 实验列表，无"够了"的判据 | 停止规则/VOI 未投影 |
| ABSTAIN 9.3% | StakesProfile + exit_condition/deadline | "不下结论"三个字 | 四要素文案未投影 |
| 模型透明度 8.4% | BeliefEdge 9 类 + provenance | 中间变量可见但关系"太线性" | 边类型 + 系数来源未投影 |

## 3. 用户故事

1. **作为「风险厌恶型」创业者（不信任判断层）**，我希望每个概率数字都明确标注"这是校准概率还是模型信念分、样本多少、什么证据会改变它"，这样我才不会被 0.6/0.7 的小数点差异锚定、做出超过我风险承受力的投入。（依据：U00050/U00533/U00611）
2. **作为「行动派」产品经理（复杂/低频层）**，我希望默认只看到"当前判断 / 为什么 / 最大未知 / 下一步做什么 / 什么会改变判断"五句话，点开才看 belief/utility 细节，这样我能在三分钟内做一个决定，而不是先学一套方法论。（依据：U00008/U00063/U00126）
3. **作为「怀疑主义者」投资人（不信任判断层）**，我希望系统在 ABSTAIN/WAIT 时同时告诉我"为什么不决策、最低成本的下一步、停止研究条件、最晚决策点"，这样我才能判断它是"严谨"还是"把责任推回给我"。（依据：U00002/U00100/U00244）
4. **作为「完美主义者」独立开发者（有价值但需改进层）**，我希望看到每个关键权重/系数"是谁定的、什么来源、是否经我确认"，LLM 提出的参数明确标"待确认"，这样我才愿意把模型当决策参考而不是黑盒。（依据：U00116/U00309/U00652）
5. **作为「探索实验型」企业管理者（有价值但需改进层）**，我希望每个实验建议都附带"哪种结果会改变我的决策 + 停止条件"，这样"信息增益"能被翻译成"商业价值"，而不是让我无限补证据。（依据：U00169/U00554/U00657）

## 4. 需求池

### 4.0 落地约束（对所有需求生效）

- 只落在现有五层：**CLI（`cli.py`）/ API（`api.py`）/ runtime 输出投影（`runtime.py` SolveResult 系列）/ domain 展示词表（`domain/base.py` `ActionState`）/ 文档**。
- 不引入新框架；UX 需求必须映射到**可断言的工程动作**（字段/模板/测试）。
- 已落地基线（v1.2.x）不重复提：API envelope、`/health` 版本派生、prediction 单次落库、`ActionState` 五态 + `map_decision_type_to_action_state`、`/v1/solve?advanced=true`、`StakesProfile` + Adaptive ABSTAIN、Model Critic gate、Decision Ledger、`BeliefEdge`、`calibration_status`、ModelParameter provenance、CLI 命令族、20+ API 端点。

### 4.1 P0（必须做，最多 5 条）

#### P0-1 默认 5 段输出合同（Progressive Disclosure 落地）

- **评语依据**：复杂度 1,046（10.5%）+ 速度 640（6.4%）+ ABSTAIN 928（9.3%）"字段太多 / 只想做个决定 / 流程太慢"（U00001/U00008/U00126/U00314）。
- **现状**：V11 §5.1 已定义 5 段合同，`advanced=true` 双层投影已存在；但默认投影仍输出技术对象堆叠，无"当前判断/为什么/最大未知/下一步/什么会改变判断"结构。
- **需求**：为 `SolveResult` 默认投影（非 advanced）新增 5 段文案模板，复用 `ActionState`（ACT/TEST/HOLD/WAIT/STOP）作"当前判断"标签；`mode=EXPLORE/OPERATE` 切换第 4 段措辞（"最小验证动作" vs "下一步行动"）。
- **验收标准（可测试）**：
  1. `vencertia solve` 与 `POST /v1/solve`（默认，`advanced` 缺省）返回含 `current_judgment / rationale / biggest_unknown / next_step / change_condition` 五键的投影结构；
  2. 五键均非空且可逐键断言；`current_judgment` 取值 ∈ `ActionState` 五态；
  3. `advanced=true` 时仍返回完整 `advanced_view`（不回归）。
- **预估文件面**：`runtime/runtime.py`（投影层）、`api.py`、`cli.py`、新增 `runtime/presentation.py`（模板常量）、`tests/`（投影断言）。

#### P0-2 概率可信度文案模板（calibration_status 中文映射 + 概率语义）

- **评语依据**：概率可信度 1,068（10.7%）+ 不信任判断层 800（8%）"校准概率还是内部评分 / 虚假精确感"（U00001/U00116/U00533/U00998）。
- **现状**：`Belief.calibration_status` 5 态（UNCALIBRATED/LOW_SAMPLE/DOMAIN_CALIBRATED/USER_CALIBRATED/VALIDATED）已存在但**不投影到任何输出**。

## 5. 待确认问题（需用户拍板）

1. **交付形态**：v1.3 是否继续 **CLI + API 优先**，还是需要补一个 Web UI？评语中"界面/页面/字段太多"（复杂度/维护成本）强烈指向交互层，但现有产品无 Web 界面——这决定 P0-1 的 5 段合同是落在 CLI/API 投影，还是落在前端组件。
2. **EXPLORE onboarding 优先级**：复杂度痛点（10.5%）是否值得在 v1.3 先做一个 EXPLORE 模式的 onboarding/简单模板（`mode=EXPLORE` 默认隐藏 prior/posterior/utility 术语），还是把 onboarding 后置到 v1.4？
3. **概率展示策略**：默认是否**隐藏精确百分比、只显示 Low/Moderate/High 等级**（V11 §5.1"范围/等级 > 单点小数"），还是保留数字但强制带校准标签？这直接关系到风险厌恶型（怕被锚定）与理性分析型（要数字）的取舍。
4. **P0-5 技术债的 P0 定位**：是否接受把"开发者体验技术债清零"占用一个 P0 名额（与用户价值类 P0 并列），还是将其降为 P1、把名额让给"实验建议可见化（9.4%）"？
5. **集成范围**：集成需求（6.9%）是"无 UI/CLI 导入入口"还是"真·CRM/邮件自动同步"？后者属于新框架/长期投入，本 PRD 建议 P2-5 单独立项，需确认。
6. **ActionState 词表对齐**：现有代码 `ActionState` 是五态（ACT/TEST/HOLD/WAIT/STOP），而 V11 §5.2 建议词表是六态（ACT/EXPERIMENT/WAIT/HOLD/PIVOT/KILL）。是否在 v1.3 把展示词表向 V11 六态对齐（TEST→EXPERIMENT、STOP→PIVOT/KILL 拆分），还是维持五态不动？
