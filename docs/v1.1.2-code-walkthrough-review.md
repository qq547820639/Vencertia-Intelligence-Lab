## 1. 执行摘要

Vencertia v1.1.2 是一个**完成度很高、且工程纪律异常严格**的"校准优先"决策运行时。三层分离（REALITY / DECISION INTELLIGENCE / CAPABILITY）在代码中是真实落地的：Repository 是唯一写入口（`repositories/base.py`），确定性引擎纯函数化（`decision_engine.py`、`uncertainty_engine.py`），Capability/Provider 是候选产出者（`capabilities/base.py`、`providers/factory.py`）。v1.1 的 Claim Binding 四态、Provider Composition Root、Research Planner/Stop、Decision Sensitivity、可观测性与 L0–L2 基准，**绝大部分都已在代码中实现并有测试覆盖**。

但审查同时发现几处**"文档承诺了、代码没实现/没验证"的实质缺口**，以及一批工程深化与 UX 优化项。核心结论：

1. **T01–T05 施工图（`TASK_BREAKDOWN_NEXT.md`）整体落地，但存在 3 处明确 GAP + 若干"未验证"项**（详见第 4 节核对表）：
   - **GAP-1**：`MODEL_PROVIDER` 环境变量名在文档/施工图中与代码不一致（代码只认 `VENCERTIA_MODEL_PROVIDER`，`config.py:167`）。用户照 README 设置 `MODEL_PROVIDER=openai_compatible` 会**静默回退 mock**。
   - **GAP-2**：P1-8 承诺的 `decision_sensitivity_signal` 停止信号在 solve/run_plan 主链路**恒为 0.0**——两个真实调用点构造 `RoundSummary` 时从未传入 `decision_result_before/after`，该信号只在 `research_stop.py` 内部被引用、从未被喂数据。
   - **GAP-3**：PostgreSQL 后端无集成测试，且 PG 迁移只建 `entities`+`event_log`（`0002_pg.sql`），不建 v1.1 专表；`Release Gate I（SQLite+PG parity）` 实际未验证。
2. **"是否已全部实现"：主体已实现，但离"生产级闭环"还差一段**（第 5 节）：真实 Provider 接入路径、L1 真实数据闭环、Postgres 测试、CallRecorder 的 tokens/cost 实际填充、全链路 async 化等，均有明确深化空间且以代码为依据。
3. **UX 优化**（第 6/7 节）：API 错误响应未走统一 envelope、`/health` 硬编码 `"version":"1.0.0"`、Prediction 双重写、ConfidenceCalibrator 重复实现、缺 `__main__.py`、L2 CLI 空跑等，已按 P0/P1/P2 排序给出可执行清单。

## 2. 整体印象与主观评价

**这是一份"以正确性为第一优先级"的代码库，而非"以功能堆叠为第一优先级"。** 三点印象最深：

- **一致性纪律极高**：几乎每个模块顶部 docstring 都锚定 ADR 编号与设计文档章节；`object.__setattr__` 绕过 `validate_assignment` 的地方都有注释说明为什么（如 `belief_engine.py:259`、`domain/belief.py:70`）；四态绑定、N/A 语义、乐观锁、`UNBOUND_EVIDENCE` 显式留痕这些"诚实性"约定贯穿全库。
- **测试是"验收驱动"的**：`tests/test_integrity_v112.py` 直接把 TASK_BREAKDOWN 的 P0/P1/P2 验收点逐条映射成 14 个测试（文件头注释列出 1–14 的映射表），`test_runtime_never_calls_repository_private_list` 甚至用静态扫描断言 `repo._list` 不在运行时/能力层出现。这种"把验收点写成测试"的做法非常扎实。
- **但也存在"过度自证"的局部**：`test_version_single_source`、`test_health_exposes_runtime_and_api_contract_versions` 用 `assert data["version"] == "1.0.0"` 把 `/health` 里一个**历史兼容别名**固化成契约，反而锁死了一个会让用户困惑的行为（见 6.1）。

主观判断：**这是一个"内核正确、边界未打磨"的工程**。核心决策引擎与数据契约经得起推敲；主要风险不在算法正确性，而在**文档与代码漂移、错误路径的一致性、以及"承诺了但主链路没接线"的信号**。

### 3.3 src/vencertia/（92 py，核心走读对象）

#### 3.3.1 入口与装配

- **`__init__.py`**：版本单一来源 `__version__="1.1.2"`、`__api_contract_version__="1.1"`，有测试锁定三处一致（`test_integrity_v112.py:660-670`）。
- **`config.py`（232 行）**：`Settings` 为 frozen dataclass，`from_env()` 完整覆盖所有 `VENCERTIA_*` 环境变量，默认全离线（`model_provider="mock"`）。10 维排序权重、绑定三阈值、三段鲁棒性阈值、provider 韧性、`opportunity_cost_enabled=False` 全部可配置。**问题**：`policy_version` 默认 `"1.0"`（注释解释是为 v1.0 ledger 契约兼容），导致 `BeliefUpdateRecord.policy_version` 在 solve 里被写成 `"1.0"`（`runtime.py:1064`），与 belief_engine 内部写死的 `"1.1"`（`belief_engine.py:379`）并存——policy 版本语义分裂，值得单独治理。
- **`container.py`（151 行）**：单一 Composition Root，`Settings→Repository→ProviderBundle→EngineBundle→SolveOrchestrator→FastAPI/typer` 装配链清晰；`providers` 属性装配时发 `PROVIDER_SELECTED` 事件；`call_recorder` 注入 provider bundle（P1-7）。**问题**：`_build_repository` 中 `db_dsn == "sqlite:///:memory:"` 才走 InMemory，其余都走 SQLite；Postgres 仅在 `postgres_dsn` 存在时尝试，且 `PostgresDisabledError` 直接 re-raise（loud fail，注释明确这是刻意行为）。
- **`api.py`（516 行）** / **`cli.py`（521 行）**：见 3.3.6 与第 6 节。
- **无 `__main__.py`**：`python -m vencertia` 会失败（No module named `vencertia.__main__`）；README 全程用 `python -m vencertia.cli` 与 `[project.scripts] vencertia` 绕过。

#### 3.3.2 domain/（REALITY 层，25 个 py，1610 行）

- `base.py`：`VencertiaBaseModel` 统一 `extra="forbid"` + `validate_assignment=True` + `use_enum_values=True`，全部枚举集中定义（Scope/EvidenceType/AuthorityLevel/Verification/Direction/DecisionType/ConvergenceStatus 等）。
- `belief.py`：`Belief` 用 `@model_validator(after)` 把 `probability` 与 `posterior` 同步、`confidence` 与 `uncertainty` 同步（`belief.py:68-73`）——这是 `object.__setattr__` 在各引擎里出现的原因，设计自洽但**绕过校验赋值是脆弱点**。
- `evidence.py`：`Evidence` 完整含 v1.1 的 freshness/dedup 字段与 v1.1.2 的 `project_id/company_id` 租户隔离字段。
- `binding.py`：`BindingStatus` 四态（BOUND/AMBIGUOUS/REJECTED/UNBOUND_EVIDENCE）+ `UNBOUND` 作为**代码级名字别名**（映射到 `UNBOUND_EVIDENCE`，非字面值别名），docstring 详述 GAP-01 语义——这是全库最精心处理的一块。
- `context.py`：`ContextBundle`/`ContextBundleV11` 下沉到 domain 层（P2-15 修层依赖环），`runtime/context.py` 仅保留 Builder 并 re-export。
- 其余 `claim/decision/experiment/prediction/research/decision_trace/observability/calibration/evidence_conflict/belief_update/company/founder/memory/objective/project/action_outcome/convergence` 均齐备，`__init__.py` 全量导出（167 行 `__all__`）。

#### 3.3.3 repositories/（持久层，1295 行）

- **`base.py`（684 行）**：`Repository` Protocol 定义了完整接口；`EntityStoreMixin` 用 generic `entities` 表实现全部 CRUD；`in_transaction` 用 `_txn_depth` 深度计数实现嵌套事务合并（P2-17）；`add_evidence` 实现 P0-3 写边界（PROJECT/CUSTOMER 无 `project_id` → `ValueError`）；`list_evidence` 实现读边界（project-owned + shared WORLD/MARKET/COMPANY_CASE）。
- **`sqlite.py`（320 行）**：`_store` 乐观锁（expected_version UPDATE + rowcount==0 判 StaleWrite）；`_maybe_commit` 在 `_txn_depth==0` 才 commit；`_txn` 真正的 BEGIN/COMMIT/ROLLBACK；**override** `save_binding/get_binding/list_bindings/save_belief_update_record/list_belief_update_records` 到 `claim_bindings`/`belief_update_records` 专表。
- **`postgres.py`（167 行）**：`_store`/`_txn` 用 psycopg3；**未 override** binding/belief_update_record 方法 → 走 generic `entities` 表。**迁移只执行 `0002_pg.sql`（entities+event_log），不执行 `0003_v1_1.sql`**（`migrations/__init__.py:run_migrations` 的 postgres 分支）。
- **`memory.py`**：InMemory 快照回滚事务，`_store` 乐观锁语义与 SQLite 基本对齐（但"空槽 + expected_version≠1"时 InMemory 抛 StaleWrite、SQLite 会 INSERT，存在**边角 parity 差异**）。

**三后端一致性判定**：SQLite 用专表、Postgres/Memory 用 generic 表，**行为等价但存储路径不同**；Postgres 路径无测试、无真实库验证，`Release Gate I` 未验证（见 5.3）。

#### 3.3.4 runtime/（DECISION INTELLIGENCE，6207 行，核心）

`runtime.py`（1134 行）的 `solve` 闭环链路与施工图 §6.1 完全对应：

```
Context → Compile → Persist → Critical → ResearchPlan → [round: Search/Dedup/Bind/Conflict/Belief/Stop]
→ Converge → Decision+Trace → Sensitivity → (ABSTAIN→Experiment) → PredictionLedger → Persist
```

- 研究循环把**外部 IO（search/retrieval）放在事务外**（`run_solve_round`），**确定性 mutation batch 放进 `in_transaction`**（`runtime.py:365-509`），P2-17 原子性实现正确。
- 各引擎职责单一且纯函数化：`belief_engine`（Beta-Bernoulli + 冲突折减 + `BeliefUpdateRecord`）、`decision_engine`（EU + margin + ABSTAIN + `build_trace`）、`uncertainty_engine`（best-vs-second impact）、`convergence_engine`（7 态）、`experiment_optimizer`（validation→rank→propose）、`prediction_ledger`（snapshot hash + immutable resolve + correct）、`calibration_engine`（Brier/ECE/bins）、`confidence_calibrator`、`claim_binding`（Extract→Match→Validate→Link）、`context_ranker`（10 维）、`research_planner`、`research_stop`（8 类信号）、`evidence_dedup`、`conflict_engine`、`decision_sensitivity`（翻转阈值 + 三段鲁棒性）、`observability`（CallRecorder）、`opportunity_cost`（默认关闭）。
- v1.1.2 的 P2-16 拆分了 4 个服务（`compilation_service`/`research_service`/`decision_evaluation_service`/`outcome_settlement_service`），facade 委托、`SolveResult` schema 冻结，拆分后行为一致（有逐字段比对测试 `test_integrity_v112.py:783-811`）。

#### 3.3.5 capabilities/ + providers/（CAPABILITY 层）

- `capabilities/`（476 行）：`Capability` Protocol（`run → CapabilityResult`，候选产出、无写权）；`DecisionCompiler` 把问题文本编译成候选 Objective/Decision/Claims/Beliefs/Experiments；`build_capability_registry` 挂 6 个能力。**注意**：`capabilities/base.py:10` 已正确 `from vencertia.domain.context import ContextBundle`（P2-15 层依赖环已修）。

### 3.4 tests/（67 py）

测试组织分四层：顶层单测（`test_*.py` 36 个，引擎/域/仓库/API/CLI/benchmark）+ `tests/qa/`（10 个 v1.0 QA）+ `tests/qa_v11/`（7 个 v1.1 QA）+ `tests/qa_v111/`（6 个 RC QA）+ `tests/qa_v112/`（2 个 v1.1.2 QA）。**覆盖率倾向**：引擎纯函数与边界路径覆盖极好（`test_sensitivity_robustness_v111.py`、`test_binding_status_v111.py`、`test_qa_v111_*_edges.py` 专门打边界）；API 用 `fastapi.testclient.TestClient` 做集成；CLI 用 `typer.testing.CliRunner` 做集成。

**已确认的测试缺口**：
1. **Postgres 后端无集成测试**——`test_v11_extra.py:163-167` 只测 `PostgresRepository(dsn=None)` 抛 `PostgresDisabledError`（禁用路径），从未对真实 PG 库跑任何 CRUD。
2. **`decision_sensitivity_signal` 无测试覆盖**——`test_integrity_v112.py` 只测 `claim_coverage` 与 `source_quality`（P1-8 的 10/11 号测试），未测该信号（因为它主链路恒 0）。
3. **`MODEL_PROVIDER` 环境变量名无测试锁定**——测试都用 `Settings(model_provider=...)` 直设，无一条测试用 `os.environ["MODEL_PROVIDER"]`，所以这个 doc-vs-code 漂移逃过了所有测试。
4. **CallRecorder 的 tokens/cost 无真实来源**——`openai_compatible.py` 从不回填 token 用量/成本，`ProviderCallRecord.tokens/cost` 恒为空/0（见 5.5）。

## 5. 代码质量与深化迭代空间（问题 2）

### 5.1 真实 Provider 接入路径（P1，已部分就绪）
`openai_compatible.py` 与 `http_search.py` 是"构造测试通过、未真实调用"（DELIVERY_REPORT 已诚实声明）。若要接真实 OpenAI/LiteLLM/商业搜索，**唯一需要做的是补真实端到端冒烟 + 把 `_parse_json` 的 json_schema 约束与 `DecisionCompiler` 的 schema 打通**——当前 `generate_structured` 传的 `schema={"kind": "compile_decision"}` 是"kind 标签"而非真实 JSON Schema（`openai_compatible.py:71-72` 会把整个 dict 当 `json_schema` 发给端点），真实 OpenAI 会因 `{"kind": ...}` 不是合法 JSON Schema 而报错。**这是接真实 provider 的第一个拦路石**。

### 5.2 L1 数据闭环（P1）
`l1.py:171-175` 把 5 个 v1.1 指标硬编码为 `None`（诚实 N/A），但意味着 **L1 "6/6" 实际只验证了 6 条合成决策重放的 option/status 正确性**，Claim Binding Accuracy / Research Efficiency / Evidence Yield / Belief Delta Quality / Decision Change Precision 全部没有真实数据源。要真正闭环，需要：① 给 `l1_cases.jsonl` 增加 binding/efficiency/yield/delta 的 gold 标注字段；② 让 `_run_case` 真正跑 research/binding 而非只用 T0 evidence 直灌。

### 5.3 PostgreSQL 路径测试（P0）
- `run_migrations(conn, "postgres")` 只执行 `0002_pg.sql`，**不建 `claim_bindings`/`belief_update_records` 专表**；Postgres 走 generic `entities` 表存储 binding/belief_update_record，与 SQLite 专表路径**行为等价但未验证**。
- `test_v11_extra.py:163` 只测禁用路径。`Release Gate I（SQLite+PG parity）` 在 `TASK_BREAKDOWN_V1_1_2.md:140` 被列为发布闸门，但**无一条真实 PG 测试支撑**。
- 建议：引入 `pytest-postgresql` 或 CI 里起一个 PG 容器，跑与 `test_repositories.py` 等价的 CRUD/乐观锁/事务回滚用例。

### 5.4 并发与异步（P2）
全库**只有一个 `async def`**（`api.py:503` 的 stale-write 异常处理器），所有路由是 sync handler（FastAPI 丢线程池跑）。对 SQLite（`check_same_thread=False` 单连接）当前够用，但接真实 LLM/搜索的慢 IO 时，**同步阻塞会占满线程池**。深化方向：把 provider IO 层改为 `httpx.AsyncClient` + async handler，或至少给 `openai_compatible`/`http_search` 加并发上限与超时预算。

### 5.5 可观测性深度（P1）
CallRecorder 记录 kind/provider/model/request_id/latency/success/retry，红线（不记 prompt）守住了；但 **tokens/cost 恒为 0/空**——`openai_compatible.py` 从不解析 `usage` 字段回填。真实计费与用量分析无从谈起。

### 5.6 安全（P2）
- `Dockerfile` 无 `USER`（以 root 跑）；`api_key` 通过 header 传递但无 redaction 审计（好在 CallRecorder 不落 key）。
- `health()` 暴露 `model_provider`/`policy_version`（无害），但无鉴权——API 整体无认证/授权层（对单机原型可接受，多租户前必须补）。
- `source_audit.json`/`integration_manifest.json` 无敏感内容。

### 5.7 其它代码层质量项（P2）
- `convergence_engine.py:48-51`、`127-131` 的 `e.status in (None,"PROPOSED","RUNNING") or e.status == "PROPOSED"` 后半句是**冗余死条件**。
- `belief_engine.py:315-316`、`evidence_policy.py:114` 用 `__import__("math").exp/log` 内联 import，属风格异味（顶部 import 即可）。
- `context.py:50` 与 `context_ranker.py:144` 对 authority 表各写了一份（9 级权重表重复 4 处：`context.py`/`context_ranker.py`/`evidence_dedup.py`/`evidence_policy.py`），应抽到单一常量。
- `ConfidenceCalibrator`（`confidence_calibrator.py:56-94`）与 `CalibrationEngine.calibrate`（`calibration_engine.py:216-252`）的 bins/piecewise 逻辑**完全重复**，DRY 违例。

## 6. UX / 开发者体验优化空间（问题 3）

### 6.1 API 响应格式不一致（P0）
`api.py:3` 声明"统一响应 envelope `{code, data, message}`"，`ApiResponse`/`ok()`/`fail()` 也定义了；但**错误路径几乎全部用 `raise HTTPException(status_code, detail=str(exc))`**（`api.py:162-163/175-176/182/200/205/221-222/232/257-258/293-294/304-307/341-342/358/371/395/408-409/457-458/465-466/483`），客户端拿到的是 FastAPI 默认 `{"detail": "..."}`，**与成功响应的 `{code,data,message}` 是两套格式**。`fail()` 只在 `stale_write_handler`（`api.py:509`）被用了一次。这是最常见的"文档说统一、实际两套"。

### 6.2 `/health` 的 `"version":"1.0.0"` 硬编码别名（P1）
`api.py:143` 硬编码 `"version": "1.0.0"`（注释称 v1.0 健康契约别名），并被 `test_integrity_v112.py:679` 锁死。用户在 v1.1.2 的 `/health` 里看到 `version=1.0.0` 会误以为跑了旧版。建议：改为派生 `"version": vencertia.__version__`，或明确重命名为 `"legacy_version"`。

### 6.3 Prediction 双重写 + 字段缺失（P1）
`PredictionLedger.register`（`prediction_ledger.py:69`）已 `save_prediction(entry)`，`runtime._register_predictions`（`runtime.py:1101-1106`）又再 `save_prediction(entry, expected_version=1)` 一次。副作用：① 冗余写；② 第一轮落库的预测缺 `domain/model_tag/module_tag`；③ 通过 `/v1/predictions`、`prediction create` 直调 `register()` 的预测**永久缺这三字段**，导致 `calibration_engine.update_all_scopes` 按 `model_tag/domain/module_tag` 分层时它们全归入一个 `None` 桶。

### 6.4 缺 `__main__.py`（P2）
`python -m vencertia` 报 `No module named vencertia.__main__`。补一个 `__main__.py` 转发到 `cli.app()` 即可对齐常见 `python -m <pkg>` 心智模型。

### 6.5 L2 CLI 空跑（P2）
`cli.py:423-428` 的 `benchmark run --level L2` 直接 `L2Runner().due_report()`，**未注入 repo → 恒返回 `[]`**，用户跑一条命令只看到 `[]`。应接线 repo（或明确提示"需先 register"）。

### 6.6 错误信息友好度（P2）
`ValueError("A decision requires at least two options.")`（`decision_engine.py:70`）在 API 侧会变成裸 400 `{"detail": "..."}`（无 envelope）。多数错误信息是英文技术短语，对中文用户友好度一般。建议在 API 层统一异常→envelope 映射时顺带做用户可读话术。

### 6.7 文档导航一致性（P2）
README 文档索引同时指向大写（`architecture.md`）与小写（`domain-model.md`）两套 canonical；T05"保留小写连字符 canonical"未完成。建议统一 README 索引 + 顶部加一张"文档↔代码模块"对照表。
