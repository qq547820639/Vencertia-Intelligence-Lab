# Addendum for `Memory Write.docx`

## AGENTV10.2 USER KNOWLEDGE RUNTIME INTEGRATION

**Version scope:** AgentV10.2 additive integration / Vencertia User Knowledge Runtime V1.0 / AgentV10.1 Memory semantics preserved.

### V10.2 PRECEDENCE AND SCOPE

This appendix is authoritative only for User Knowledge Runtime integration. All non-conflicting AgentV10.1 Memory rules remain in force. The Memory Write Engine retains its existing role and is **not renamed** to a generic Knowledge Write Engine.

### USER KNOWLEDGE IS A COMPOSITE READ LAYER

For product and retrieval purposes, Vencertia may expose a `User Knowledge` layer. It is a composite projection over canonical stores such as:

- FounderProfile
- MemoryRecord
- Project KB / Project Snapshot
- Evidence
- Assumptions
- Experiments
- Actions
- Decisions
- Financial Snapshots
- authorized network/profile data where applicable

Do not create a second canonical `KnowledgeRecord`, `KnowledgeType`, `KnowledgeStatus`, or generic `knowledge_records` table merely to unify these domains.

### MEMORY REMAINS THE DURABLE PERSONALIZED KNOWLEDGE STORE

`MemoryRecord` continues to own curated durable user/project knowledge. Conversation, Project State, Evidence, Assumptions, Experiments, Actions, Decisions, Financial Snapshots and Startup Intelligence remain separate according to existing AgentV10.1 rules.

### USER KNOWLEDGE RUNTIME WRITE FLOW

Conceptually:

```text
Raw Conversation / Event / Result
→ MemoryCandidate extraction
→ Proper-Store Test
→ Memory Write Engine
→ WRITE / MERGE / SUPERSEDE / CONFLICT / REJECT / EXPIRE / ARCHIVE
→ authorized MemoryRecord persistence
→ Profile / Snapshot / Context refresh signals when material
→ future Context Builder retrieval
```

Specialists and Orchestrator may emit candidates. Only the Memory Manager/runtime commits Stable Memory.

### RUNTIME-ONLY CANDIDATE ENVELOPE

Runtime may wrap a canonical `MemoryCandidate` with non-canonical metadata such as:

- source_types
- evidence_ids
- semantic_key
- proper_store
- access_class
- origin_agent

This envelope exists for authorization, routing, deduplication, conflict handling and privacy. It does not replace or expand the canonical Memory Type taxonomy.

### CONTEXT BUILDER AS THE READ GATE

A0–A10 should normally consume relevant Memory through a task-specific `ContextBundle` generated by the Context Builder. Do not let Specialists query or serialize the complete Memory store by default.

Retrieval must enforce:

- user/tenant ownership
- project scope
- status and validity
- privacy/access class
- task relevance
- token budget
- explicit conflict surfacing

ACTIVE Memory is preferred. SUPERSEDED/ARCHIVED Memory is historical. CONFLICTED Memory must never be presented as unqualified truth.

### USER KNOWLEDGE PROJECTION

A user-facing Knowledge Base view may aggregate FounderProfile, active global Memory, project Memory, project summaries and unresolved conflicts. This object is a read projection only. Edits/corrections must route back to the owning canonical domain and Memory Write workflow.

### CROSS-PROJECT LEARNING

Project-specific knowledge stays project-specific unless deliberately promoted. Cross-project learning must use already-approved Memory Types such as `LESSON`, `EXCLUSION_RULE`, `CAPABILITY`, `RESOURCE`, `CONSTRAINT`, `PREFERENCE`, `RED_LINE`, or another existing valid type. Do not add `GOAL`, `FOUNDER_FIT`, or `ANTI_PATTERN` as new top-level MemoryType values in this release.

### FOUNDER PROFILE SYNCHRONIZATION

A material USER_GLOBAL write involving Founder facts, capabilities, resources, constraints, preferences or red lines may emit a `founder_profile_refresh_required` runtime signal. The Founder domain service owns canonical FounderProfile synchronization. Do not create a parallel profile inside Memory.

### PROJECT SNAPSHOT / ROUTING / STATE REFRESH

A material Memory change may emit runtime signals for:

- project_snapshot_refresh_required
- context_refresh_required
- routing_reassessment_recommended
- state_reassessment_recommended

These signals request recomputation; they do not grant Memory Write Engine authority to make strategic decisions or mutate project stage directly.

### FINANCIAL BOUNDARY

The latest/current price, CAC, margin, conversion, working capital and similar temporal financial metrics remain canonically represented in versioned Financial Snapshots. Durable financial lessons or durable validated records may enter Memory without competing with the latest Financial Snapshot as current truth.

### PRIVACY

Memory remains PRIVATE by default. Runtime permission metadata may classify a record as INTERNAL, MATCHABLE or PUBLIC for controlled projection. A9 receives only permissioned MATCHABLE/PUBLIC signals for exposure. A8/external research tools must not receive raw private Memory unless explicitly required and permitted; minimize the payload.

### FINAL V10.2 MEMORY RULE

User Knowledge Runtime unifies **access**, not **truth ownership**. Preserve the canonical boundaries that make AgentV10.1 auditable.
